## 1. 文档目的

本文将赛题原始要求转化为可设计、可开发、可测试、可验收的软件需求，确定 Scry 的用户、业务范围、功能边界、质量属性、数据与接口约束，并为《软件功能设计文档》《软件产品说明书》《软件功能测试报告》和《软件性能（核心指标）测试报告》提供统一基线。

需求等级定义如下：

- P0：赛题硬性要求或安全底线，缺失将导致产品不具备参赛完整性。
- P1：形成完整运维闭环所需的重要能力。
- P2：增强创新性、实用性或演示效果的扩展能力。

## 2. 赛题需求解读

赛题要求开发部署于操作系统的智能运维 Agent，以自然语言连接管理员与操作系统，通过 MCP 将感知与运维动作封装为工具，并重点解决大模型推理和执行的不可控问题。

赛题明确提出五项基本功能：

1. OS 环境深度感知。
2. MCP 运维插件化。
3. 安全意图二次过滤。
4. 最小权限代理执行。
5. “接收指令 - 感知环境 - 推理决策 - 安全校验 - 执行结果”的链路溯源。

赛题同时要求：采用 B/S 架构；运行于 LoongArch + 麒麟高级服务器操作系统 V11；严禁未授权修改关键配置；具备 Prompt Injection 防护。评分重点为功能完整性 55%、创新与实用性 25%、文档与演示 20%。

## 3. 产品目标与范围

### 3.1 产品目标

Scry 应实现“可感知、会分析、能受控执行、可验证、可追溯”的智能运维闭环：

```text
自然语言请求
  -> 身份与输入安全检查
  -> 指标/日志/链路/OS 实时取证
  -> Agent 推理与根因分析
  -> 工具和参数安全裁决
  -> 审批与最小权限执行
  -> 执行后验证
  -> 证据、记忆和审计留存
```

### 3.2 纳入范围

- 浏览器端统一运维工作台。
- 指标、日志、链路、基础设施、消息队列、仪表盘和告警查询。
- Agent 诊断、规划和受控操作。
- MCP Server、内置工具和远程 MCP 插件。
- Prompt Injection 检测、意图分类、命令复检、审批和审计。
- `scry-ops` 受限账户和固定包装器。
- 证据评分、证据处置、证据约束重答和 TopoMem 运行记忆。
- Loop 自动化流程、调度、条件、并行、循环、审批、执行和验证。
- 故障模拟、准确性评测以及麒麟 V11/LoongArch64 原生部署。

### 3.3 不纳入范围

- 不提供无边界的通用 root Shell。
- 不允许模型直接持有系统 root、数据库管理员或 Docker Socket 权限。
- 不以模型输出替代操作系统权限、策略和审批。
- 不承诺替代数据库备份、灾难恢复、终端防护或企业身份平台。
- 不把调试故障数据当作真实生产遥测。

## 4. 用户角色

| 角色 | 主要目标 | 权限边界 |
|---|---|---|
| 系统管理员 | 配置组织、模型、MCP、主机、策略、Loop 和审计 | 可管理平台配置，但操作仍受审批和最小权限约束 |
| 运维编辑者 | 观测系统、诊断故障、运行授权流程、处置证据 | 不可修改管理员专属安全配置 |
| 只读查看者 | 查看遥测、告警、仪表盘和授权结果 | 不可执行变更或维护组织配置 |
| 安全审计人员 | 按用户、组织、Trace 和事件检查决策链 | 默认只读，不接触模型 Key、SSH 私钥等秘密明文 |

所有资源必须包含组织边界；角色授权由服务端执行，前端隐藏按钮不能作为唯一控制。

## 5. 典型业务场景

### 5.1 磁盘空间异常

管理员提出“帮我清理系统垃圾”。系统必须先查询磁盘指标、目录占用和近期系统错误，区分普通缓存、应用日志和数据库关键文件。删除或清理动作必须匹配预配置操作、触发审批、使用受限包装器，并在执行后重新检查磁盘使用率和关键服务状态。

### 5.2 僵尸进程堆积

Agent 读取进程和父子关系，结合系统日志识别未正确回收子进程的父进程。系统应优先给出修复父进程 `SIGCHLD/wait` 处理的建议；若需要重启，必须走服务白名单和审批，不得直接使用 `kill -9` 批量处理。

### 5.3 磁盘 I/O 异常

系统关联主机 I/O、应用延迟、数据库等待和 Trace 路径，识别资源瓶颈与上游传播结果，输出有证据的根因、处置顺序和恢复验证标准。

### 5.4 配置漂移

系统比较配置摘要、变更时间与服务异常，不得直接修改关键配置文件。修复必须通过管理员登记的工具或流程，保留审批、参数哈希、执行输出和复验结果。

### 5.5 提示词注入攻击

当消息、附件或工具输出要求忽略系统规则、泄露提示词、绕过审批或解码执行载荷时，系统必须拒绝请求或挂起证据，记录风险规则和 traceId，且不得将该内容作为上位指令交给模型执行。

| ID | 优先级 | 需求 | 验收标准 |

## 8. 数据需求

### 8.1 核心数据实体

- 用户上下文：userId、orgId、role、token（仅请求期）。
- Thread 与消息：标题、角色、结构化消息、创建和更新时间。
- 证据：来源、内容哈希、评分、状态、关系、操作和修订记录。
- 记忆：类型、作用域、服务、内容分块、来源、关系、拓扑边和检索运行。
- MCP 插件：名称、URL、加密认证头、超时、启用状态。
- 主机与策略：主机指纹、加密凭证、工具策略、审批需求。
- 工作流：定义、版本、触发器、并发策略、运行状态和步骤事件。
- 安全审计：traceId、事件类型、裁决、风险分、输入哈希和结构化摘要。

### 8.2 数据保护

模型 Key、MCP 认证头、SSH 密码和私钥必须使用主密钥加密保存。API、日志、证据、A2UI 和审计不得返回秘密明文。遥测与 Agent 配置应按组织隔离，调试数据必须具有独立标识和清理边界。

## 9. 外部接口需求

- Web Console 通过统一 HTTP 入口访问 Query Service 和 Agent Service。
- OpenTelemetry Collector 接收 OTLP 指标、日志和链路。
- Query Service 向 Agent 提供受当前用户 JWT 约束的查询接口。
- MCP 使用 Streamable HTTP 协议和 JSON Schema 工具参数。
- SSH 仅连接固定 `scry-ops` 账户并校验主机密钥指纹。
- PostgreSQL 保存 Agent 运行状态，WASM SQLite 保存轻量配置与审计，ClickHouse 保存遥测。

## 10. 约束与假设

1. 目标机须具备麒麟 V11、LoongArch64 编译工具链和可用软件源。
2. Query Service 因 CGO 依赖应在目标 LoongArch64 主机原生构建。
3. Node.js 22 需在目标架构可用，Agent 采用纯 JS/WASM 依赖避免本地原生扩展阻塞。
4. 外部大模型的可用性、排队和答案质量不完全由 Scry 控制；安全裁决不得依赖外部模型。
5. 生产受管主机必须由管理员预先安装并校验 `scry-ops`。
